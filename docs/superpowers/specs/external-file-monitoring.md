# External file monitoring and conflict handling

Status: **design independently reviewed; probe and reducer implemented and component-tested; service and native integration incomplete**. See ../../verification/external-file-monitoring.md for executed evidence. No complete monitoring, A-07/A-08 or desktop acceptance is claimed here. Prepared 2026-09-09 against the current document-owned storage/undo, shared panes, expected-byte atomic saves, uncertain-publication state, and recovery checkpoints. Routine design approvals are replaced by documented review under BUILD_PROMPT; this document does not authorize remote publication.

## Scope and invariants

A-07 needs proactive external-change detection and safe explicit reload/conflict choices. A-08 needs actionable permission, missing, rename and symlink states. Existing AtomicFileStore detects conflicts at save, refuses final-component symlinks and read-only mode bits, validates parent identity, and retains exact attempted bytes/evidence after uncertain publication. Those protections remain authoritative. Its final check/rename race against arbitrary writers remains a documented limitation; a watcher cannot close it.

One EditorDocument owns one monitor registration and one disk-state value. Panes display the same document status; splitting, focusing and collapsing cannot create more watches, comparisons, modal alerts, baseline mutations or recovery records. Scratch documents without an original URL have no ordinary-file watch. Pending Save As destinations retain their existing explicit retry verification; if different from the original URL they are not silently adopted or treated as saved by this monitor.

Monitoring never writes document files, changes originalBytes/savedText/encoding/BOM, clears pendingPublication, changes dirty state, clears recovery, registers undo, or resolves a conflict by itself. Disk read-only status does not make the in-memory editor read-only: edits remain possible and Save As remains available. No automatic original-file autosave, dirty reload, forced overwrite, recursive directory scan, script execution, cloud download request, or permission adjustment is added.

## Native approach comparison

| Approach | Fit | Decision |
| --- | --- | --- |
| DispatchSource filesystem-object sources on file and parent descriptors, plus bounded reconciliation | Direct vnode signals for the retained inode; parent wakeups discover replacement at the original name. Events may coalesce and are hints, so re-open/check the pathname. Explicit descriptor cancellation ownership is required. | Choose for the current custom AppKit document model. |
| NSFilePresenter with NSFileCoordinator | Higher-level coordination and move notifications; appropriate for NSDocument/cooperating coordinated access. Adopting it properly would also change read/write coordination and lifecycle; it is not a substitute for checking uncoordinated writers. | Defer; do not bolt a presenter onto the current uncoordinated save transaction and claim protection. |
| FSEvents, or periodic polling alone | FSEvents provides broader directory history with coalescing/rescan obligations. Polling is simpler but repeats metadata I/O, has latency, and cannot identify provenance. | No recursive FSEvents inventory. Use lightweight reconciliation only as a fallback to vnode hints. |

These are design choices inferred from Apple's [Dispatch Sources guide](https://developer.apple.com/library/archive/documentation/General/Conceptual/ConcurrencyProgrammingGuide/GCDWorkQueues/GCDWorkQueues.html), [filesystem-source factory](https://developer.apple.com/documentation/dispatch/dispatchsource/makefilesystemobjectsource(filedescriptor:eventmask:queue:)), [file coordinators and presenters guide](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemProgrammingGuide/FileCoordinators/FileCoordinators.html), and [FSEvents event handling](https://developer.apple.com/library/archive/documentation/Darwin/Conceptual/FSEvents_ProgGuide/UsingtheFSEventsFramework/UsingtheFSEventsFramework.html), consulted 2026-09-09. These APIs are platform dependencies, not copied third-party code/assets. Runtime behavior on supported macOS versions still needs real-file tests.

## Ownership, scheduling and bounded work

Use a process-owned FileMonitorService serial control queue, owning registrations keyed by document UUID. EditorDocument owns a cancellation token; event callbacks weakly reference their UI owner. Each registration has an epoch, original URL, baseline revision, at most one file source and one parent source, current metadata fingerprint, last observation, and a queued-check bit. Each event handler only queues work; it does not read contents or call AppKit. Every potentially blocking filesystem operation—including path/symlink resolution, volume checks, open/openat, stat/access, F_GETPATH, read, revalidation and close—runs on the bounded workers, never MainActor or the control queue. The control queue performs only in-memory scheduling/token accounting and dispatch-source configuration using worker-prepared descriptor leases. Watch setup is asynchronous and may fail after registration; failure produces explicit monitoring-unavailable state. Watch `.write`, `.extend`, `.attrib`, `.link`, `.rename`, `.delete`, `.revoke`; parent changes request a named-file reconciliation, not a directory enumeration.

Up to 128 document registrations, two active probe workers process-wide, one in-flight check and one coalesced pending check per registration, and at most 256 watched descriptors plus twelve reserved transient descriptors (six per admitted worker), for a maximum of 268 explicitly monitor-owned descriptors. At the registration cap, surface “Automatic monitoring unavailable for this tab; use Check File on Disk.” Manual checks use a separate one-shot request API carrying document UUID, request UUID, URL, baseline bytes/revision and completion, so the 129th document and failed-watch documents can still be checked without a registration. Admit at most 16 queued/running manual requests process-wide through the same two-worker pool. Capacity refusal and cancellation complete explicitly; each request completes once. Manual requests install no sources, and their request UUID/lifetime guards reject stale UI completion. Do not drop registration/check requests silently. Baseline Data is shared by value with existing originalBytes; do not build another full decoded String or persist private paths in diagnostics.

Coalesce bursts for 250 ms, with a two-second maximum deferral while dirty events continue. Reconcile watched paths every 30 seconds and on app activation, volume/wake hints, explicit Check, successful open/reload/save and watcher rearm. The intended metadata-only periodic optimization is not implemented: the current probe always checks exact bytes because prior observation reuse lacked baseline identity. Keep this limitation explicit until separately tested baseline-scoped reuse exists. In the intended design, metadata-only periodic probes avoid full reads when unchanged; every activation/manual check and vnode file-change hint forces exact byte comparison even if size/timestamps appear unchanged. Metadata fingerprints are an optimization, never overwrite authorization. A writer that perfectly restores metadata without a delivered event can remain undetected until a forced check; report that limit rather than promise surveillance of every transient change.

Byte comparisons stream 64 KiB chunks, retry EINTR, distinguish EOF from partial reads, check cancellation between chunks, reject >100,000,000-byte content, and check descriptor/path metadata before and after. A two-second cooperative deadline stops between syscalls. Regular files on local volumes only for automatic content monitoring; unsupported volume state is explicit. A blocking kernel read/open cannot be forcibly cancelled by Swift task cancellation or O_NONBLOCK on a regular file. The worker pool remains capped, no replacement tasks accumulate, and UI can report delayed checking. A hard wall-clock guarantee requires a separate process and is not claimed by this design.

Every result carries document UUID, registration epoch, baseline revision, observation sequence and URL. MainActor accepts only matching live registration/document/URL/baseline, and ignores stale completions after Save As, reload, close, quit freeze, or restart. Results arriving while saving/composing/quitting are coalesced for later reconciliation, without modal UI or baseline adoption. Quit neither waits for monitoring I/O nor lets late events alter the final session/recovery snapshot; veto resumes checks. Stop invalidates delivery immediately and cancels sources on their control queue. The cancel handler transfers the FD lease to bounded-worker cleanup; close occurs exactly once after any worker borrower releases the lease, never before an event/worker can finish using it. Cancellation completion does not claim the descriptor already closed. Only enqueue a close after the in-memory borrower count reaches zero; do not occupy a worker waiting for another borrower. Give ready cleanup priority when a worker becomes free. Rearm does not transfer an old FD to a new source. Reserve watch slots before opening, including opened-but-not-installed, installed, retired and cancellation-in-flight leases; only actual close releases a slot. If old/new leases would exceed 256, defer rearm without blocking the control queue and surface delayed monitoring.

Each worker reserves six transient slots before starting: primary parent and file, independent revalidation parent and file, optional moved-candidate parent and file. Volume checks use existing FDs; no extra hidden owned opens or descriptor duplication is permitted. Operations needing another owned FD must first close/release a listed lease, rather than exceed six. Worker-prepared watch FDs consume watch reservations, not transient slots; transfer ownership without an uncounted dup. The 268 bound covers descriptors this subsystem explicitly owns, not every Foundation/system-internal descriptor in the process. Count reservations as well as live descriptors in tests; two stuck workers can retain their fixed budgets but cannot trigger unbounded replacement work or freeze cancellation bookkeeping.

## Dataless-file materialization boundary

Apple documents that path metadata operations can materialize intermediate dataless folders; checking local-volume flags is insufficient. Use the documented thread-scoped materialization opt-out before path lookup or content access. See [Apple TN3150](https://developer.apple.com/documentation/technotes/tn3150-getting-ready-for-data-less-files).

`FileMaterializationGuard.perform` runs only synchronous work on its calling thread. It reads the prior policy, disables materialization for that thread, captures success/failure, and restores the prior policy before returning. Policy query/setup failures prevent work; restoration failure is an error, not a successful observation. A caller returning owned resources supplies disposal for a successful resource result whose policy restoration then fails. Thrown operations retain responsibility for partial-resource cleanup in their own defers. A failed OS restoration cannot promise the prior thread state; no process-wide policy is changed.

Standalone probe entry points and entire service worker transactions need this boundary. All new path/read/watch/candidate work remains inside it; no result or prepared source may be published before successful return. Nested typed policy errors abort the outer transaction instead of being swallowed by generic catches. EDEADLK is an explicit not-downloaded/unavailable observation. Descriptor close and lease bookkeeping remain unconditional, including when policy establishment fails; close-only cleanup does not access a pathname or materialize contents. Existing worker/FD limits remain unchanged. Real cloud accounts and placeholders have not been tested; synthetic faults and native policy inspection must be distinguished from that acceptance.

## Safe observations and identities

Add a testable synchronous PadCore probe with no AppKit dependency. It receives URL, expected original bytes and an optional previously accepted target identity. It returns an observation, never replacement originalBytes. Initial observation binds identity only after an exact comparison against bytes loaded by the editor; a file changed between load and watcher start is a conflict, not a new baseline.

Capture parent and file `(device,inode)` plus mode, size, mtime/ctime nanoseconds and relevant immutable flags. Open the canonical parent directory, then `openat` the final name with `O_NOFOLLOW | O_NONBLOCK | O_CLOEXEC`; require regular-file metadata and revalidate the resolved parent and final directory entry against the opened descriptors. Follow existing AtomicFileStore policy for initially stable parent symlinks; reject later parent resolution changes relative to the bound identity. A final symlink is never followed for monitoring/reload. An existing legacy-opened symlink buffer remains intact and receives “Source is a symbolic link; choose its regular-file target explicitly or Save As.” No silent global change to existing open semantics in the monitor task.

Classify missing path, inaccessible file/parent, nonregular target, final symlink, parent retarget, content changed, matching bytes, identical-byte inode replacement, and read changing during observation separately. Access/readonly indicators are advisory: mode bits, immutable flags and effective-access results can inform UX, but ACLs, mount state and later changes mean only the real save outcome decides whether writing succeeds. Never test writability by writing a probe into the user's directory. Permissions checks must not treat an inaccessible path as deleted.

An inode change with identical bytes is “same content, replacement file,” not proof of an app save. Re-arm the watch for the new inode after stable validation, preserve baseline bytes, and clear only the relevant content warning. A mode/parent problem can remain even when bytes match. Preserve multiple facets of state rather than collapsing changed+read-only into one mutually exclusive enum.

On rename/delete of the watched inode, an off-main Darwin `fcntl(F_GETPATH)` may supply a candidate path. Treat it as an untrusted hint: bounded local absolute path, regular no-follow target, same retained file identity and stable parent/file checks are required. No sibling directory scan, automatic name search or filesystem crawl. If unavailable, ambiguous, hardlinked, outside supported local-volume policy, or changed again, show “Original path missing or moved” and offer Locate. Candidate display alone never changes document.url, MRU, session metadata, pending evidence or save destination.

## Own saves and uncertain publication

At save start, retain the current monitor baseline/epoch and mark observation application deferred. Do not suppress events for a guessed time window. On successful save, the existing save completion first sets URL/originalBytes/savedText/savedEncoding/BOM and clears pendingPublication exactly as today. Then increment the monitor baseline revision, bind the successful URL, cancel the old watch if necessary, and queue a forced check. Delayed old events/results are rejected by epoch. Matching new bytes can clear an external-content notice, but cannot manufacture a save receipt.

On `publicationUncertain`, preserve exact PendingDocumentPublication evidence/bytes and dirty disposition. An event showing the attempted bytes does not clear it. Save remains the current exact-evidence validation followed by a fresh successful save; Save As stays create-only. Do not adopt observed disk bytes as expected save bytes, even after Keep Buffer or Locate. If a new external change occurs after a successful publication, the fresh reconciliation should report it against the now-acknowledged bytes.

## User actions and transaction rules

Use one nonmodal, accessible document status row, separate from checkpoint status, with a concise reason and applicable real actions. No alert per event, no duplicate pane warnings. UI tests identify `document.diskStatus`, `document.checkDisk`, `document.reloadDisk`, `document.openDiskCopy`, and `document.locateSource`. Names and full paths are shown only where useful locally, not written to public logs. Registry entries use `file.checkDisk` (“Check File on Disk”) and `file.resolveDiskChange` (“Resolve File Change…”). A window panel captures document UUID and observation token; it never infers a target from whichever pane later has focus.

| Observed state | Actions and safe effect |
| --- | --- |
| Content changed, clean buffer | Reload from Disk, Open Disk Version in New Tab, Keep Buffer, Check Again. Reload is explicit by default; no automatic reload setting in this subsystem. |
| Content changed, dirty or pending publication | Open Disk Version in New Tab, Save As, Keep Buffer, explicit “Discard Buffer Changes and Reload…” with Cancel default. Pending-publication warning is included in that confirmation. No force-overwrite action. |
| Missing/moved | Locate Source, Save As, Keep Buffer, Check Again. Normal Save does not recreate a previously loaded missing path automatically. |
| Read-only/inaccessible | Retain editable buffer, show Save As/Check Again and an explanation; do not chmod, escalate, or substitute empty contents. |
| Unsafe link/nonregular/parent retarget | Keep Buffer/Save As; Locate permits deliberate selection of a verified regular target. Never automatically follow a new link or changed parent. |
| Unsupported size/volume or exhausted monitoring capacity | Show explicit monitoring limitation and retain manual safe-save conflict checks; no empty or “unchanged” result. |

Keep Buffer dismisses only the current notice prominence; the observed conflict remains in the model and ordinary Save still compares against originalBytes. A new distinct observation may make the notice prominent again. Do not repeat unchanged warnings. No comparison UI is claimed unless actually wired; Open Disk Version creates a scratch tab with no original-path write capability, using an external-read decoder that recognizes a supported BOM before consulting the source's saved-byte encoding. Inspect longest markers first: reject unsupported UTF-32 BOMs rather than misclassifying their UTF-16 prefix; for UTF-8/UTF-16 LE/BE BOMs call DocumentCodec.decode without an explicit encoding so detection wins. Use savedEncoding only for BOM-less bytes. Preserve the decoded encoding/BOM on the new scratch or successfully reloaded document. Do not change explicit Reopen with Encoding semantics globally. Decode failure/unsupported size leaves all existing tabs unchanged.

Reload action captures logical document ID, URL, monitor epoch/observation, editRevision, current encoding/BOM, pending publication, original-byte baseline revision, and all attached pane selections. Reject while composition/save/quit is active, and preserve the existing macro-recording reload veto. Check recording again after asynchronous work and modal return; no external-change callback may bypass that veto. Freeze all pooled views only for the admitted reload transaction; read/decode/revalidate off-main, then request explicit discard confirmation if dirty/uncertain. Revalidate document lifetime and captured revisions after every suspension or native modal loop. Recheck the disk observation after confirmation; if disk changed again, retain buffer and refresh the conflict instead of accepting unreviewed content. Restore interactivity with existing lifecycle-aware helper on every exit.

Only a successful admitted reload changes storage/saved baseline and clears pending publication, resets bookmarks/pending composition bookkeeping, and clears native undo as existing reload does. Preserve pane identities, split axis and focus; clamp each saved selection to legal UTF16 scalar boundaries of the decoded text using existing RestoredViewState validation, without stealing focus. Re-run one document highlighter/settings update, schedule recovery/checkpoint once, and rebind monitor epoch. The discard confirmation is an explicit destructive decision; the subsystem does not promise undo of a reload. Open Disk Version and Save As provide non-destructive alternatives.

Locate is an explicit selection, not automatic rename acceptance. Stable candidate with exact originalBytes and no pending publication may update URL after a “Use This Location” action without changing text/undo/encoding/bookmarks; increment epoch and update MRU/session once. Different bytes offer Open Disk Version or explicit discard-and-reload first; no direct rebind of a dirty buffer to unrelated content. While publication is uncertain, Locate may open a disk copy but cannot redirect pending retry evidence. Successful Save As or explicit reload resolves that uncertainty through their existing semantics.

## Verification and acceptance boundaries

Implement with isolated red–green Foundation and hidden native harnesses before integrated copy. Synthetic real-file cases must cover in-place writes, atomic replacement, identical-byte replacement, renamed file/parent, delete/recreate, mode/immutable/ACL or injected access failure, hardlink ambiguity, final symlink, parent symlink retarget, FIFO, same-size/same-mtime changes, Unicode/BOM/legacy bytes, 100 MB cap and partial/EINTR reads. Inject races between stat/read/path revalidation, delayed results, clock ticks and watcher cancellation; never assert exact event counts or arrival ordering from Darwin.

Native cases: clean/dirty/pending Save As conflicts, keep-buffer then refused save, own save then concurrent external replacement, shared-pane one monitor, no duplicate parser/recovery, changed-during-confirmation, closed/quit owner, veto resumption, one-panel target after tab switch, per-pane selection clamping on reload, locate with same/different bytes, and errors retaining editability/undo/baseline. Existing SaveFailure, DirtyState, Recovery, WindowCheckpoint, Launch and shared-pane harnesses are mandatory compatibility checks. Packaged DesktopUI external-writer scenarios remain blocked until authorized macOS automation is available; simulated events and a passing build are not desktop evidence.

This draft is complete as a proposal only. The implementation plan defines ownership, interfaces, first red tests and handoff gates. Independent design review found the five reported gaps resolved and no new material issue; implementation still requires isolated behavioral red/green and code review; no requirement matrix or completion record is changed by these files.

## Independent review response — design revision only

The five findings from independent review are incorporated; implementation and runtime tests remain outstanding.

1. Recognized BOM now precedes the old saved encoding for external reload/disk copy; BOM-less data uses savedEncoding. Test LE→BE and legacy→UTF-8 BOM, plus unsupported UTF-32 prefix refusal.
2. Unregistered manual checks now have bounded one-shot request/completion semantics, including the 129th tab, watcher setup failure, capacity rejection, cancellation and stale delivery.
3. External reload preserves the existing macro-recording veto at invocation and completion, with an actual callback regression.
4. Descriptor accounting now reserves 256 watch plus 12 transient slots, explicitly covering preparation, revalidation and cancellation-in-flight leases; no undocumented four-FD assumption remains.
5. All filesystem work moves to two bounded workers; control-queue admission/cancellation stays responsive under gated path-resolution/open/volume/read stalls. Tests must prove the worker and descriptor bounds.
