# Session restoration preservation review

Reviewed 2026-09-09: `SessionStore.swift`, `SessionRestoration.swift`, `RestoredViewState.swift`, and `SessionRestorationController.swift`; focused on corrupt/versioned persistence, capacity agreement, unresolved-entry retention, stale async callbacks and local-path safety. Native startup integration is changing independently and is not implied complete by this review.

## Confirmed issue, fixed

**P1: valid native/recovered text could be rejected solely by the restoration bookmark adapter's UTF-8 reference limit.** `RestoredViewState.resolve` checked the 100 MB UTF-8 reference limit unconditionally, even with no bookmarks. Native editing and recovery accept 100 million UTF-16 units. A synthetic Windows-1252 document of 33,333,334 Euro bytes plus an initial newline is 33,333,335 bytes on disk and 33,333,335 UTF-16 units; decoded UTF-8 is 100,000,003 bytes. The file is valid within the normal loader limit and the recovery planner accepts its snapshot, but the original restore-view call threw `textLimit` before restoring either empty or populated bookmark metadata.

An isolated red regression reproduced this with the actual codec and recovery planner. The fix adds `DocumentBookmarks.init(offsets:inUTF16:)`, validates native line starts directly within 100 million UTF-16 units, and routes RestoredViewState through it. This preserves the String reference API and its existing limit. Selection clamping, scalar boundaries and reporting invalid bookmark offsets remain intact. Both empty marks and `[0,1]` restore successfully. No large fixture is tracked; tests generate the synthetic data in memory.

Verification: `scripts/swift.sh test --package-path .local/restoration-spike` passed 24 tests, zero failures, 4.009 seconds after formatting, including 13 bookmark tests, 5 restored-view tests and 6 restoration-plan tests. Exact green source/tests were copied into the main tree. Root owns the subsequent full native integration run; no unobserved result is claimed here.

## Other reviewed preservation paths

- SessionStore validates model bounds before publication, rejects corrupt/unknown/future records rather than replacing them, preserves original bytes on injected prepublication failures, and distinguishes a postpublication directory-sync failure. Canonical re-encoding checks reject extra/duplicate fields. Existing tests cover malformed/future records and failed saves; no new fault was found in those paths.
- Private storage uses owner/mode checks, final-component nofollow opens, single-link regular-file checks, bounded exact reads and identity/timestamp checks. The pinned directory is checked before publication. Arbitrary same-user processes ignoring locks can still race final checks; the existing documented boundary remains, not a newly discovered isolation guarantee.
- Planner input UUIDs are typed; serialized malformed UUIDs fail decoding. Duplicate document/window/recovery IDs and cross-kind collisions fail explicitly. Saved file paths remain load requests; matching recovery is an explicit scratch source using recovery encoding/BOM. Missing scratch recovery remains a missingRecovery item. No referenced document path is opened by the planner/store.
- The 256-record restoration capacity exceeds SessionStore's 128-tab persistence capacity, and a 33rd orphan window exceeds its 32-window capacity. Both are intentionally exposed through `exceedsPersistenceCapacity`/`needsResolution`; records are not dropped. Root must preserve unresolved data and require capacity resolution before persistence.
- Controller read callbacks are documented as read-only. `onResolved` runs only after current-generation and open-window guards; entries are removed only after successful import. Failed reads/imports retain metadata and record an error. Update/close invalidates the generation and cancels tasks/sheets. After synchronous callbacks, guards run again so callback-triggered updates do not mutate a newer entries list.
- Remove uses explicit confirmation and a throwing callback; failure retains the entry. Current native harness source covers failed read/import/removal, locate cancel, duplicate actions and late completion after update/close. This review inspected those assertions; it does not relabel source inspection as a newly executed native test.

No second material defect was confirmed in the bounded reviewed scope. Recovery restoration, path loading, unresolved removal persistence and application-wide shutdown ordering still require the root's integrated native tests; this review is not a claim of whole-application correctness.
