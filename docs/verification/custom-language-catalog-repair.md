# Custom language catalog repair and publication evidence

The Core store supports explicit repair of a known-format corrupted catalog, validation of a genuine uncertain publication, and republication of its exact attempted bytes. This is a tested Core component; owner recovery and manager UI activation remain outstanding.

Repair uses the opaque token produced by inspection. It validates the proposed definitions/overrides before publication, starts an explicit new generation/revision lineage at one, and requires the same destination, safe owned parent identity, full original leaf metadata and original bytes. A read-only leaf is refused before write callbacks. Unknown/future formats and conservative parser-invalid or duplicate-key inspection cannot acquire a repair token. Export and explicit malformed-format replacement require a separate workflow.

Pending validation requires the receiving store's destination and original AtomicFileStore evidence, checked before and after an actual stable owned read. It returns Void, not an acknowledgment or writable receipt, and never writes. Retry performs a fresh atomic save of exactly the original attempted bytes; it does not re-encode the catalog or advance generation/revision. Genuine new uncertainty carries its new evidence. An acknowledged write followed by failed readback yields a distinct evidence-free readback-unconfirmed outcome. A loaded return comes from an actual stable current read and strict decoder, not fabricated proof of a written inode. Original load/save and read-only inspection source are unchanged.
